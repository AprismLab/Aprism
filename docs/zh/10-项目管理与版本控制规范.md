# Aprism 项目管理与版本控制规范（Doc 10）

> 适用于所有 Aprism 家族仓库（`AprismLab/Aprism`、
> `AprismLab/AprismRefract`、`AprismLab/AprismJDK`、
> `AprismLab/AprismPrismate`、`AprismLab/AprismTest`）。维护者：
> BlockConnect@StarsailsClover。随 v26.4-Alpha.2 交付。本文档将项目
> 实际执行的约定固化为规范；它是契约，不是建议。

---

## 1. 版本方案

版本标识符遵循 `v<MAJOR>.<MINOR>[-Alpha.<N>]`：

- **MAJOR** 对应 20xx 线的日历年（`v26` = 2026）。
- **MINOR** 按功能线递增（`v26.1`、`v26.2`……）。
- 每条 minor 线最多交付**九个 Alpha**（`v26.X-Alpha.1` …
  `v26.X-Alpha.9`），每个都是独立发布并验证的 Pre-Release。
- **裸版本号**（`v26.X`，无后缀）是该 minor 线的正式 GA 发布。它冻结
  Alpha 工作，并作为非预发布的 GitHub Release 发布。
- 示例线：`v26.3-Alpha.1 ... v26.3-Alpha.9`，然后 `v26.3` GA。

规则：

1. 一条 minor 线内绝不复用 Alpha 编号。
2. 绝不跳过裸版本号 GA：每条交付了 Alpha 的 minor 线必须以 GA 收尾。
3. 构建坐标（`gradle.properties` 的 `aprismVersion`、
   `gradle/libs.versions.toml` 的 `aprism`、`README.md` 的
   `Version:`）必须携带相同的版本字符串，并在引入该变更集的同一提交中
   一并升级。

## 2. 分支策略

Aprism 家族对主仓库采用**主干式、仅 main**：

- 所有工作落在 `main`；没有长生命周期的功能分支，也没有来自功能分支的
  合并提交。
- 例外是 **AprismRefract**，它为每个外部 loader 使用一条长生命周期分支
  （`fabric`、`forge`、`neoforge`、`quilt`、`liteloader`），外加用于
  共享文档的 `main`。每条分支是一个独立的 loader-support `.aep`
  提供方；分支之间永不互相合并。
- 热修复（如有需要）是 `main` 上的普通提交加补丁标签，不是回溯移植
  分支。

## 3. 提交与标签

每个提交与每个发布标签都是**签名**的：

- 提交签名：`git commit -S`，使用项目 SSH ED25519 签名密钥（经
  `git log --show-signature` 验证）。
- 标签签名：`git tag -s`（签名的附注标签）；标签消息携带发布内容的
  一行摘要。
- 提交消息格式：`<type>(<scope>): v<version> - <summary>`，例如
  `feat(imc): v26.3-Alpha.7 - InterModComms for Forge/NeoForge
  parity (...)`。使用的类型：`feat`、`fix`、`refactor`、`test`、
  `docs`、`release`、`build`。
- 版本升级与其功能变更在**一个**提交中交付；标签指向该提交。

## 4. 发布流水线

发布仅由 GitHub Actions 工作流 `.github/workflows/release.yml`
产生，由推送版本标签触发：

1. 用 JDK 21 构建（`./gradlew build package`），产出名为
   `Aprism-<version>-JE-26.2.jar` 的 fat agent jar。
2. 生成 `checksums.txt`（所有产物的 SHA-256）。
3. 用 **cosign keyless**（GitHub OIDC 身份）为每个产物签名，每个产物
   产出 `.sig` + `.bundle`。
4. 发布 SBOM（`Aprism-sbom.cdx.json`，CycloneDX）。
5. 创建 GitHub Release：`-Alpha.N` 标签为 **Pre-Release**，裸版本号
   标签为正式发布。发布正文在存在时读取
   `docs/release-notes/<version>.md`（丰富版说明），否则回退到生成的
   模板。

每次发布的验证契约（维护者与 CI 消费方）：

- `sha256sum -c checksums.txt` 必须通过（注意 CRLF：在 Windows 生成的
  文件上先去除 `\r`）。
- `cosign verify-blob <artifact> --signature <artifact>.sig --bundle
  <artifact>.bundle --certificate-identity-regexp "AprismLab/Aprism"
  --certificate-oidc-issuer https://token.actions.githubusercontent.com`
  必须报告 `Verified OK`。
- 仓库在 v26.3 期间从 `NDBlockConnect/Aprism` 迁移到
  `AprismLab/Aprism`；证书身份是 AprismLab 的，旧远程 URL 经重定向
  继续可用。

## 5. 测试规则

测试是发布门槛，不是礼貌：

1. **每次发布前跑全量套件** —— `./gradlew test --rerun-tasks`（不信任
   缓存）必须报告 0 失败，然后提交才被签名并推送。
2. **测试数量被跟踪**，记录于 FACT.md 的每个 alpha（如 v26.3：430 ->
   496）。缩减套件的发布必须在会话日志中说明理由。
3. **真实游戏验证** —— MDL 驱动的冒烟 harness
   （`tools/smoke/run_smoke.sh`）启动真实 Minecraft 26.2 并附加
   agent，每条 minor 线至少报告一次 `SMOKE PASS`（v26.2 已完成；每次
   GA 前重复）。
4. Refract loader-support 分支运行各自的套件；核心的跨仓库 E2E 测试
   消费分支构建的 `.aep` 产物。

## 6. 文档规则

1. **双语，EN 权威。** 每份实质性文档同时存在于 `docs/en/`（权威）与
   `docs/zh/`（镜像，编号相同）。对其中一份的修改要求在同一发布中
   对另一份做匹配修改。
2. **文档与改动它的代码一同交付。** 新增 API 面的功能 alpha 必须在
   同一提交中扩展 Doc 01（架构）。
3. **Doc 09（已知问题）** 在每次 GA 时刷新：已关闭条目标注
   `[CLOSED in vX.Y-Alpha.N]` 并保留以便追溯；新注意事项在 GA 提交前
   添加。
4. **丰富版发布说明** 位于 `docs/release-notes/<version>.md`，适用于
   每次 GA（以及可选地用于值得注意的 alpha）。
5. 任何产物、文档或发布说明中不使用 emoji。

## 7. FACT.md 会话日志

`FACT.md`（仓库根目录，有意**不**提交 —— 它是本地工作日志）按会话
记录：

- 做了什么（`[DONE]`）、做出的决定（`[DECISION]`）、注意事项
  （`[NOTE]`）、发现并修复的 bug（`[BUG FIXED]`）；
- 测试套件的增减；
- 指导后续会话的路线图章节。

它是任何提交背后"为什么"的权威来源；git 历史是"是什么"的权威来源。

## 8. 子项目治理

| 仓库 | 角色 | 版本耦合 |
|---|---|---|
| `AprismLab/Aprism` | 主加载器/注入器；拥有版本线 `v26.X` | — |
| `AprismLab/AprismRefract` | 外部 loader-support `.aep` 提供方，每 loader 一条分支 | 针对当前 Aprism jar 构建（`align` 版本）；独立发布 |
| `AprismLab/AprismJDK` | OpenJDK 变体（AJR）+ AprismateAgent 设计/构建 | 自有版本线；设计自 Aprism v26.4 起跟踪 |
| `AprismLab/AprismPrismate` | 渲染/视觉伴生 | 自有版本线 |
| `AprismLab/AprismTest` | 跨仓库测试夹具 | 跟随主仓库 |

规则：

1. 主仓库在构建期从不依赖子项目；集成通过产物（`.aep` 文件、jar）与
   跨仓库 E2E 测试进行。
2. 每个子项目保留自己的 README + LICENSE，并在有发布时遵循相同的
   签名/发布约定。
3. 暂停某子项目的工作（如 Aprism BE 直到九月逆向工程里程碑）作为
   `[DECISION]` 记录于 FACT.md 并附恢复条件 —— 暂停的工作被冻结，
   永不删除。

## 9. 安全与披露

1. **契约式失败安全。** 加载器与 agent 代码绝不使宿主游戏或 JVM
   崩溃；失败被记录并隔离（见 Doc 06 原理说明书）。
2. **原生修改披露。** BE 原生修改在线上服务存在封禁风险；Doc 01
   §13.2 与 Doc 09 携带该披露。
3. 仓库中无密钥；CI 使用 GitHub OIDC 进行签名，无长期密钥。

## 10. 本文档的变更控制

本文档仅通过类型为 `docs`、scope 为 `conventions` 的有意提交变更，
且两份语言副本必须一起变更。不允许追溯改写已记录的决定；更正作为新的
`[NOTE]` 条目追加。
