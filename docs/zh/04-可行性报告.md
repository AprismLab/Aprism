## 1. 执行摘要

Aprism Loader 是一个多版本、多平台的 Minecraft 模组开发框架，它在单一产品之下统一 Java Edition（JE）模组 loader，并引入原生的 Bedrock Edition（BE）客户端/服务端模组能力。本报告评估该产品在技术上是否可构建、在法律上是否可辩护、在市场上是否可行，以及在维护上是否可持续。

总体结论为**有条件推进**，按版本分述如下：

- **JE 统一 loader：高度可行。** 所有关键底层技术（javaagent、Mixin、超集清单、多 loader 构建）均已被 Fabric、Quilt、NeoForge 与 MultiLoader-Template 验证。无需任何全新研究。风险在于工程范围，而非可行性。
- **BE Windows 客户端注入：可行。** Amethyst、OnixClient 与 BetterRenderDragon 已证明代理 DLL 劫持加 MinHook/libhat 是一条具备生产能力的实现路径。UWP 沙盒是约束，而非阻断项。
- **BE Android 注入：可行但需附注。** root 路径通过 Zygisk + ShadowHook 已在生产环境中得到强化。非 root 容器路径（NMLauncher 模式）可行，但因 APK 重打包而处于法律灰色地带。两条路径在 BE 更新面前都很脆弱。
- **BE iOS 注入：边缘可行。** TrollStore 支持在窄幅 iOS 版本范围内进行 sideload。目前不存在规模化的社区 BE iOS mod loader。建议仅作研究，不予发布。
- **BE macOS/Linux 客户端：不可行。** 这些平台上不存在 Bedrock 客户端二进制。超出范围。
- **BE 主机端：不可行。** 完全锁定。超出范围。
- **BDS 服务端模组：可行。** LeviLamina（1553 stars）与 LiteLoaderBDS 已公开、规模化地展示了直接链接式的服务端模组模式。
- **JE-to-BE 转换：部分可行。** Script API 无法表达 Fabric 等价的功能（超出 JSON 之外的自定义方块/物品/维度）。要达到功能对等必须使用原生钩子。完全自动化转换无法实现；人工辅助转换可以实现。

主要的工程风险是 **BE 版本维护**：每一次 Bedrock 更新都会改变偏移与签名。这一项风险决定了 BE 支持是否可持续。缓解该风险需要社区维护的签名数据库与自动化头文件生成（即 LeviLamina/BedrockAnalyzer 模式）。

推荐的交付顺序是**先 JE，其次 BE Windows，再次 BE Android，iOS 仅作研究**。每个阶段都有明确的 go/no-go 准则。在 BE Windows 已证明能够跨至少两次 Mojang BE 发布版本保持可持续更新节奏之前，项目不应承诺投入 BE Android 或 iOS。

## 2. 范围与假设

### 2.1 在范围内

- JE 统一 loader，通过超集清单与 Mixin 支持 Fabric、NeoForge、Forge、Quilt 与 LiteLoader。
- BE 客户端注入：Windows（P0）、Android（P1）、iOS（P2 研究）。
- 通过直接链接实现的 BDS 服务端模组。
- JE-to-BE 转换工具链（人工辅助，非完全自动化）。
- 通过 GitHub Releases 分发的独立桌面发行物，使用 cosign 签名。

### 2.2 在范围外

- macOS、Linux 与主机端的 BE 客户端模组（无可用二进制或完全锁定）。
- 通过 Microsoft Store、Apple App Store 或 Google Play 分发（政策禁止；见 5.2 节）。
- 修改 Realms 服务器或官方推荐服务器。
- 重新分发任何 Mojang 拥有的二进制、资产或商标。

### 2.3 假设

- 目标用户群体具备技术素养：既有的 JE 模组用户能够安装自定义启动器，BE 高级用户愿意在应用商店之外安装独立软件。
- Mojang 在既有 EULA 下继续允许客户端 JE 模组，且不会追溯性地禁止基于 javaagent 的 loader。
- Microsoft 不将 Xbox Live 执法扩展至封禁在单人或第三方多人游戏中使用 JE 模组的用户。
- 项目至少有一位具备 C++/ARM 逆向工程能力（用于 BE 工作）的贡献者，以及一位具备 JVM/Mixin 专长（用于 JE 工作）的贡献者。
- GitHub Releases 仍然是模组工具可接受的分发渠道。
- Bedrock 版本的发布节奏大致维持在每年 4-6 个主要版本。

若被证伪会改变结论的假设列于第 10 节。

## 3. 技术可行性

### 3.1 JE 统一 Loader

**可行性：高。** 无需全新技术。

JE 架构使用一个挂载到调校过的 OpenJDK 运行时的 javaagent。loader 兼容性（Fabric、NeoForge、Forge、Quilt、LiteLoader）通过一个表达各 loader 元数据模型的超集清单来实现，并结合 Mixin 完成运行时字节码转换。这与 Fabric 和 Quilt 已在生产中使用的方案相同。MultiLoader-Template 证明了单一模组源码树可以在构建时面向多个 loader，从而验证了超集清单这一前提。Architectury API 进一步证明跨 loader 抽象层是可行且被采纳的。

关键工程工作是集成与工具，而非研究：
- 超集清单 schema 与按 loader 的投影。
- 多 loader 共存时的 Mixin 协调。
- 从单一源码树产出各 loader 产物的构建工具。
- 用于挂载 javaagent 的启动器集成。

剩余风险低且有界：因为组件技术已部署至数百万用户，行为已被充分理解。

### 3.2 BE 客户端注入（按平台）

| 平台 | 可行性 | 证据 | 主要风险 |
|---|---|---|---|
| Windows | 可行 | Amethyst（531 stars）、OnixClient、BetterRenderDragon 使用代理 DLL 劫持 + MinHook + libhat | UWP 沙盒；每次 BE 更新后的签名漂移 |
| Android（root） | 可行但需附注 | Zygisk + ShadowHook（由 ByteDance/TikTok 在生产环境中强化） | 需要 root；跨 BE 更新脆弱 |
| Android（非 root） | 可行但需附注 | NMLauncher 演示了容器化方案 | 法律灰色地带（APK 重打包）；跨 BE 更新脆弱 |
| iOS | 边缘可行 | TrollStore 仅在 iOS 14.0-16.6.1/17.0 上可用 | 每个版本需重新注入；无规模化社区 loader；维护负担高 |
| macOS | 不可行 | 无 Bedrock 客户端二进制 | N/A |
| Linux | 不可行 | 无 Bedrock 客户端二进制 | N/A |
| 主机端 | 不可行 | 完全锁定；不支持 sideload | N/A |

Windows 路径最为稳固：社区标准做法（`ratification`/`libhat` 风格的代理 DLL 劫持、MinHook 跳板、进程内 mod host）已在至少三个独立项目中得到文档化与复现。UWP 沙盒限制了文件系统与注册表访问，但当 loader 与游戏进程同址时并不阻止 DLL 劫持。loader 代码必须运行在 UWP 应用容器之外，这与独立桌面分发模型相一致。

Android root 在技术上是最具生产强化程度的路径，因为 Zygisk 与 ShadowHook 由大型团队（ByteDance）为规模化生产用途而维护。代价是用户群仅限 root 用户，规模较小。

通过容器化实现的 Android 非 root 路径（NMLauncher 模式）扩大了用户群，但需要重新打包 Minecraft APK，这在 EULA 与 Google Play 政策下属于明确的法律灰色地带。该路径在技术上可行，但只有在经过明确的法律审查后才能推进。

iOS 边缘可行：TrollStore 支持在窄版本范围内进行无签名 sideload，需要按版本重新注入，且不存在规模化的社区 BE mod loader 来验证该方案。建议仅作研究原型。

### 3.3 BE 服务端（BDS）模组

**可行性：高。** LeviLamina（1553 stars）与 LiteLoaderBDS 已证明直接链接 BDS 二进制是一种可行的、公开运营的模型。BDS 由 Mojang 作为专用服务端二进制单独分发，且服务端模组的法律风险低于客户端注入（无 Xbox Live ToS 暴露，无客户端修改）。

无需注入：loader 直接链接 BDS 可执行文件并暴露模组 API。主要风险与 BE 客户端工作相同（版本漂移），但 LeviLamina 通过 BedrockAnalyzer 自动生成头文件的做法展示了一种可持续的缓解模式。

### 3.4 JE-to-BE 转换

**可行性：部分。** 完全自动化转换无法实现。

Bedrock Script API 被刻意限制。它无法表达超出 JSON 定义内容之外的自定义方块、物品或维度，也无法执行 Mixin 在 JE 上所支持的运行时字节码转换。依赖 Fabric 式深度钩子的功能（自定义渲染、子系统替换、非原版行为覆盖）需要对 Bedrock 二进制进行原生钩子，这意味着转换产物本身是一个 BE 原生模组，而非可移植脚本。

现实的转换范围：
- JSON 内容（通过行为包定义的方块、物品、生物群系）：可自动化。
- 可由 Script API 表达的简单游戏逻辑：可自动化，但需人工审查。
- 自定义渲染、自定义 GUI、深度子系统钩子：不可自动化；需手写原生代码。

转换工具应被定位为**人工辅助**，而非自动。它降低了机械移植工作量，但无法消除接收端对 BE 工程师的需求。该功能的市场需求尚未被证实（见 4.3 节）。

### 3.5 BE 版本维护

**风险：高。这是主要的工程挑战。**

每一次 Bedrock 更新都会改变函数偏移、vtable 布局与符号签名。若不进行主动维护，每一次 BE 更新都会使 loader 失效。这不是一次性风险：在产品整个生命周期内，这是按发布版本反复出现的成本。

证明该问题困难的证据：
- Amethyst 的维护者以逆向工程负担为由部分转为闭源。
- LeviLamina 投入 BedrockAnalyzer 来按版本自动生成头文件，这是唯一被证明可持续的模式。
- BE 在主要发布周期内大约每 4-6 周发布一次更新。

所需的缓解措施：
1. **签名数据库。** 一份按 BE 发布版本编号、社区维护的函数偏移与签名数据库，并带有来源追踪。
2. **自动化头文件生成。** 一个 BedrockAnalyzer 风格的工具，读入新的 BDS/客户端二进制并产出更新后的头文件，将人工逆向工程仅限于异常情况。
3. **社区逆向工程池。** 单一维护者不足够；项目必须招募并培训多名逆向工程贡献者，以避免 bus factor 失败。
4. **更新就绪 CI。** 一套回归测试框架，在每次新 BE 发布后 24 小时内运行，并按组件报告损坏情况。

如果在 BE Windows 发布前这些缓解措施未到位，BE 产品线将在 2-3 个 BE 发布版本内进入维护死亡螺旋。

## 4. 市场可行性

### 4.1 JE 模组市场

庞大且成熟。Fabric、NeoForge 与 Forge 合计服务数百万玩家。Modrinth 托管 30,000+ 模组，CurseForge 托管 100,000+。分发基础设施已建立，用户群体理解如何安装模组。

跨 loader 统一的需求真实且可观察：
- MultiLoader-Template 被不希望为每个 loader 维护独立源码树的模组作者广泛采用。
- Architectury API 正是为抽象 loader 差异而存在，并被大量跨 loader 发布的模组使用。
- 模组作者在社区调查中持续将 loader 碎片化列为首要痛点。

Aprism 的 JE 价值主张（一份清单、一次构建、所有 loader）针对的是已被证实的作者侧痛点。用户侧需求较弱，因为玩家已有可用的 loader；Aprism 的用户侧吸引力在于便利与统一管理，而非能力。

### 4.2 BE 模组市场

供给不足。官方 Script API 被刻意限制，无法表达定义 JE 风格模组的功能。Amethyst 与 LeviLamina 相对于 BE 玩家基数而言只属于小众受众。

移动端 BE（Android 与 iOS）拥有最大的 Bedrock 玩家基数，但模组场景最小，因为进入的技术门槛（root、sideload、容器安装）远高于安装一个 JE 模组。机会真实，但采用情况不确定：最想要 BE 模组的用户恰恰最不具备安装它们的能力。

### 4.3 跨版本需求

不确定。JE 玩家很少愿意玩 BE（机制不同、内容对等性不同）。想要模组的 BE 玩家可能缺乏进行原生注入的技术能力。JE-to-BE 转换功能在技术上有意思，但其市场需求尚未被证实。它应被视为面向少数希望将 JE 模组移植到 BE 的作者的开发者便利功能，而非主要的面向用户能力。

### 4.4 竞争格局

| 竞争者 | 版本 | 平台 | 许可证 | 状态 | Aprism 优势 |
|---|---|---|---|---|---|
| Fabric | JE | 跨平台 JVM | Apache-2.0 | 活跃，成熟 | Aprism 将 Fabric 与其他 loader 统一；非替代关系 |
| NeoForge | JE | 跨平台 JVM | LGPL | 活跃，成熟 | Aprism 统一；超集清单 |
| Forge | JE | 跨平台 JVM | LGPL | 活跃，成熟 | Aprism 统一；超集清单 |
| Quilt | JE | 跨平台 JVM | Apache-2.0 | 活跃 | Aprism 统一；超集清单 |
| Prism Launcher | JE（启动器） | 桌面 | GPL-3.0 | 活跃，成熟 | Aprism 是 loader + 启动器；Prism 仅启动器 |
| Amethyst | BE 客户端 | Windows | 部分闭源 | 活跃，小众 | Aprism 面向多平台 BE；开放签名数据库 |
| OnixClient | BE 客户端 | Windows | 专有 | 活跃，小众 | Aprism 是开放框架；OnixClient 是模组包 |
| LeviLamina | BE 服务端 | Windows/Linux BDS | LGPL | 活跃，小众 | Aprism 在单一产品下整合客户端与服务端 |
| LiteLoaderBDS | BE 服务端 | Windows BDS | LGPL | 维护模式 | Aprism 同时覆盖客户端与服务端 |
| NMLauncher | BE 客户端 | Android（非 root） | 专有 | 活跃，小众 | Aprism 通过法律审查正式化该方案 |

Aprism 的差异化在于范围：单一产品覆盖 JE 统一、多平台 BE 客户端以及 BE 服务端，并附带开放的签名数据库。没有既有竞争者覆盖此面。风险在于广度稀释深度：每个细分领域都已有专注的竞争者，Aprism 必须在每个领域都达到质量对等才能具有相关性。

## 5. 法律与监管可行性

### 5.1 Minecraft EULA 分析

Minecraft EULA 区分从零创作的模组（允许）与包含实质性 Mojang 代码的修改（禁止）。

- **JE 模组：明确允许。** Fabric、Forge 与 Prism Launcher 均在此解读下合法运营。Aprism 不得重新分发修改过的 Minecraft jar；它必须针对用户自备的游戏文件运行。这与 Prism Launcher 使用的模型相同。
- **BE 客户端修改：法律灰色。** EULA 4(c) 禁止赋予不公平优势的客户端修改。模组 loader 本身并不赋予优势，但在其上运行的模组可能会。loader 默认不得启用作弊功能，并必须显著披露反作弊与官方服务器可能将任何客户端修改视为违规。
- **BDS 服务端模组：被容忍。** LeviLamina 与 LiteLoaderBDS 公开运营。BDS 是独立的可下载二进制，且服务端模组不触及 Xbox Live。这是法律风险最低的 BE 细分领域。

### 5.2 平台商店政策

- **Microsoft Store Policy 10.2** 禁止对其他应用执行动态代码注入的应用。Aprism 无法通过 Microsoft Store 分发。这与 Prism Launcher 的分发模型一致。
- **Apple App Store 2.4.5(iv)** 禁止执行或向其他进程注入代码的应用。Aprism 无法通过 App Store 分发。iOS 分发将仅限 TrollStore sideload，而后者本身依赖于窄幅 iOS 版本范围。
- **Google Play** 政策同样限制修改其他应用的应用。非 root Android 路径（APK 重打包）无法通过 Play 分发。

结论：独立桌面下载是唯一法律上安全的分发渠道。这不是 Aprism 独有的限制；这是模组工具的标准模型。

### 5.3 Xbox Live 与账号封禁风险

对 BE 客户端模组而言是真实的。Xbox Live 服务条款将客户端修改视为违规，可能导致账号停用。这适用于连接到 Realms、推荐服务器以及任何集成 Xbox Live 的多人游戏的 BE 客户端。对单人与 LAN 风险较低，对不触及客户端的 BDS 服务端模组风险为零。

Aprism 必须：
- 在安装程序、首次运行 UI 与文档中披露封禁风险。
- 对 BE 客户端安装默认采用离线或仅 LAN 模式。
- 在任何 BE 客户端连接到 Realms 或推荐服务器之前明确警告用户。

### 5.4 分发合法性

独立桌面下载在法律上是安全的（Prism Launcher 先例）。GitHub Releases 作为 CDN 是可接受的。通过 Modrinth 镜像也是可接受的。分发必须：
- 不使用 Mojang 品牌、徽标或商标。
- 不捆绑 Mojang 二进制或资产。
- 要求用户提供其自身合法获取的游戏文件。
- 对发布物签名（cosign）以提供防篡改的供应链。

### 5.5 Realms 与官方服务器

Realms 无法被模组化：用户不控制服务端二进制。修改过的 BE 客户端连接到 Realms 面临账号封禁风险（5.3 节）。官方推荐服务器（Hive、CubeCraft 等）运行自己的反作弊并封禁修改过的客户端。Aprism 必须将 Realms 与推荐服务器视为客户端模组的禁区，并在 UI 中明示。

### 5.6 知识产权

只要模组不包含实质性 Mojang 代码，模组归其创作者所有。Aprism 的角色是提供 loader 与工具；它不对模组主张所有权。Aprism 自身不得重新分发 Mojang 代码、资产或商标。从 BE 二进制生成的签名数据库与头文件是这些二进制的派生作品，必须谨慎处理：仅包含函数签名（而非反编译源码）的头文件是 LeviLamina 式做法，也是最安全的实际模型。

得分最高的两项风险（R1、R2）均为 BE 版本维护。这印证了 3.5 节：BE 可持续性是最需要管理的单一风险。若 R1 与 R2 无法缓解，BE 产品线不应发布。

### 7.2 团队规模估算

分阶段计划的最小可行团队：
- JE：2 名贡献者（1 lead，1 build/tooling）。
- BE Windows：2 名贡献者（1 lead/RE，1 mod API）。
- BE Android：1 名贡献者（与 BE Windows RE 共享）。
- BDS 服务端：1 名贡献者（可与 BE Windows 共享）。
- 签名数据库 / 头文件生成器：1 名贡献者（共享 RE）。
- Infra/CI/release：1 名贡献者（兼职）。
- 文档：1 名贡献者（兼职）。

现实下限：4-5 名活跃贡献者，其中至少 2 名具备逆向工程能力。单一维护者模型对 BE 产品线不可行；Amethyst 先例表明单一维护者无法在 BE 更新中持续承担逆向工程负荷。

### 7.3 基础设施

- GitHub 仓库与 Releases 作为主 CDN。
- GitHub Actions CI 用于构建、测试与发布签名。
- 基于 cosign 的发布签名，附带文档化的公钥。
- 签名数据库仓库，按 BE 发布版本编号的数据并附带来源元数据。
- Issue 跟踪器与文档站点（GitBook 或同等方案）。
- 可选的 Modrinth 镜像用于 JE 产物。

Alpha 阶段不需要付费基础设施。成本仅在规模化时变得重要（镜像带宽、若后续需要企业级签名则需签名密钥 HSM）。

## 8. 分阶段交付建议

### Phase 0（Alpha 1-3）：JE 基础

范围：JE 统一 loader、超集清单、多 loader 构建工具、基础启动器集成。仅在 JE 上验证基础。

Go/no-go 准则：
- JE loader 能从单一安装运行 Fabric、NeoForge、Forge、Quilt 模组。
- 跨 loader 的 20 个流行模组代表性样本运行无相对原生 loader 安装的回归。
- 构建工具从单一源码树产出各 loader 产物。
- 法律审查未识别 EULA 或分发阻断项。

### Phase 1（Alpha 4-6）：BE Windows 客户端

范围：BE Windows 客户端注入、mod API、当前 BE 发布版本的签名数据库。在支持最好的平台上验证 BE 概念。

Go/no-go 准则：
- loader 在当前稳定 BE Windows 发布版本上运行。
- 至少 5 个参考模组可加载并运行。
- 后续一次 BE 发布版本的签名数据库更新在该版本发布后 7 天内完成。
- 更新就绪 CI 在新 BE 发布后 24 小时内报告损坏情况。
- 封禁风险披露已在安装程序与首次运行 UI 中审查并发布。

若 7 天签名更新准则未达成，不得进入 Phase 2；先重新审视逆向工程流程与工具。

### Phase 2（Alpha 7-9）：BE Android + BDS 服务端

范围：先做 BE Android root 路径；非 root 容器路径在法律审查后进行。通过直接链接实现 BDS 服务端模组。

Go/no-go 准则：
- Android root 路径在当前稳定 BE Android 发布版本上运行。
- 非 root 路径以法律审查签署为门。
- BDS 服务端 loader 运行参考服务端模组。
- 签名数据库覆盖当前 BE 发布版本的 Windows、Android 与 BDS。

### Phase 3（PreRelease）：转换 + iOS 研究 + 打磨

范围：JE-to-BE 转换工具（人工辅助）、iOS 研究原型、文档完成、UX 打磨。

Go/no-go 准则：
- 在 5 个 JE 模组的参考集上，转换工具相对手工移植按可度量倍数降低人工移植工作量。
- iOS 原型在至少一个受支持 iOS 版本上运行，不承诺发布。
- 全部 8 份文档集文档完成并审查。

### Phase 4（Release）：v26.0 稳定版

范围：v26.0 稳定版发布、社区入驻、签名数据库维护贡献者指南、长期支持政策。

Go/no-go 准则：
- Phase 0-3 准则全部在至少两次 BE 发布版本上持续满足。
- 贡献者指南已发布，且至少一名外部贡献者已提交签名数据库更新。
- 发布签名与签名数据库完整性的安全审查已完成。

## 9. Go/No-Go 建议

**结论：GO，有条件。**

在以下条件下推进 Aprism Loader：

1. **JE 优先。** Phase 0 必须完成并满足其 go/no-go 准则，之后才能投入任何超出研究的 BE 工程投入。JE 风险低，即使 BE 永不发布也能展示产品价值。
2. **BE Windows 是 BE 的 go/no-go 门。** 在 BE Windows 已证明能够跨至少两次 Mojang BE 发布版本保持可持续更新节奏（以 7 天签名更新准则衡量）之前，不得承诺 BE Android 或 iOS。
3. **签名数据库与头文件生成器必须在 BE Windows 发布前到位。** 这些不是发布后的改进；它们是发布阻断项。没有它们，R1 与 R2 将迫使 BE 产品线陷入维护失败。
4. **仅独立分发。** 不进入 Microsoft Store、Apple App Store 或 Google Play。在商店政策下这是不可谈判的。
5. **封禁风险披露是发布阻断项。** 在任何 BE 客户端构建分发之前，安装程序、首次运行 UI 与文档必须向 BE 客户端用户披露 Xbox Live 封禁风险。
6. **非 root Android 路径在发布前需要明确的法律审查**，因为 APK 重打包属于法律灰色地带。
7. **iOS 在 Release 之前仅作研究。** 无发布承诺。

若条件 1-5 满足，项目可行并应推进。若条件 3 无法满足（无签名数据库 / 头文件生成器），BE 产品线应被去范围为仅 BDS 服务端，该领域维护负担较低。
